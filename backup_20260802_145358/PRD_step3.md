# PRD — 3단계: 사용자 프로필 및 레시피 저장

## 개요
사용자 프로필을 생성하고, 2단계에서 생성된 레시피를 프로필에 저장/조회/관리할 수 있는 기능을 제공한다. 이 단계부터 OpenRouter API 호출은 없으며, 순수 애플리케이션 데이터(인증, 저장, 조회) 기능이다.

## 목표
- 사용자가 자신을 식별할 수 있는 최소한의 프로필을 만든다.
- 마음에 든 레시피를 저장하고, 나중에 다시 꺼내볼 수 있다.

## 범위
**포함**
- 사용자 식별(가입/로그인) 및 프로필 정보 관리
- 레시피 저장 / 목록 조회 / 삭제
- 저장 시 원본 재료 목록·생성 시각 등 메타데이터 보존

**제외 (다른 단계 담당)**
- 이미지 인식 (1단계)
- 레시피 생성 (2단계)

## 사용자 플로우
1. 최초 사용 시 프로필 생성 (닉네임 필수, 식단 선호·알레르기는 선택 입력).
2. 로그인 상태에서 2단계 결과 화면의 "저장하기"를 누르면 레시피가 프로필에 저장된다.
3. "내 레시피" 화면에서 저장된 레시피 목록을 확인한다 (제목, 저장일, 요약).
4. 목록에서 레시피를 클릭하면 상세(재료·조리단계) 확인 가능.
5. 더 이상 필요 없는 레시피는 삭제할 수 있다.

## 데이터 모델
```
User {
  id: string
  nickname: string
  dietaryPreferences?: string[]   // 예: 채식, 할랄
  allergies?: string[]
  createdAt: datetime
}

SavedRecipe {
  id: string
  userId: string
  recipe: Recipe        // 2단계 PRD의 Recipe 구조 재사용
  sourceIngredients: string[]  // 저장 당시 1단계 인식 재료 목록
  savedAt: datetime
}
```

## 기능 요구사항
1. 사용자 식별 방식 결정 필요 (이메일/비밀번호 간편 가입 또는 익명 로컬 프로필 중 택1 — 구현 단계에서 확정).
2. 프로필 생성/수정 화면: 닉네임(필수), 식단 선호·알레르기(선택).
3. 레시피 저장 API: 2단계 `Recipe` 객체 + 원본 재료 목록을 `userId`에 연결해 저장.
4. 저장된 레시피 목록 조회 (최신순 정렬), 삭제 기능.
5. 동일 레시피 중복 저장 방지 또는 허용 여부는 구현 시 정책 결정 (기본: 중복 허용, 저장 시각으로 구분).

## 비기능 요구사항
- 저장된 데이터는 영속 저장소(DB)에 보관하며 세부 DB 종류는 이 PRD 범위 밖 — 구현 단계에서 결정.
- 사용자 개인정보(알레르기 등 민감 정보 포함)는 본인만 조회 가능하도록 접근 제어.

## 성공 기준
- 프로필을 만든 사용자가 2단계에서 생성한 레시피를 저장하고, 재방문 시 동일 레시피를 다시 확인할 수 있다.
- 저장된 레시피를 삭제하면 목록에서 즉시 사라진다.

## 리스크 / 참고 사항
- 인증 방식(이메일 가입 vs 익명 프로필)에 대한 결정이 아직 없음 — 구현 착수 전 확정 필요.
- 이 단계는 OpenRouter API와 무관하므로 별도의 API 키/모델 의존성이 없다.
